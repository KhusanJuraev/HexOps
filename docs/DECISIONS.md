# Decisions and assumptions

Requirement gaps or ambiguities, and the default chosen for each. Newest entries
go at the bottom. When a decision is revised, the original text stays and an
update is added, so the history is kept.

| ID | Topic | Decision | Why |
|----|-------|----------|-----|
| D-01 | Requirements source | The product requirements (an internal Uzbek document) define the modules, fields, status flow, UI/UX and data model. They were reconciled with this file and the README: projects have type, structured scope and start date; reports have type, CVSS, bounty and evidence; notes have tags and an optional project link; the editor has Markdown/Split/Preview modes plus mobile tabs. | One written source for scope. The internal planning documents are not part of the public repository. |
| D-02 | Delivery order | The work was delivered in stages: 1 scaffold → 2 auth, shell, i18n, theme → 3 Projects → 4 Reports & attachments → 5 Notes & shared Markdown editor → 6 Search & Dashboard → 7 PDF → 8 integration checks. Later decisions follow in order. | One module per stage keeps each stage testable. |
| D-03 | Sessions | Opaque random tokens in a `user_sessions` table, not JWTs. Only HMAC-SHA256 digests are stored. | Sessions can be revoked at once (logout, password change), and a DB leak does not expose usable tokens. |
| D-04 | CSRF | A per-session synchronizer token: readable `hexops_csrf` cookie + `X-CSRF-Token` header, checked against the stored digest on every non-safe method. Also an Origin/Referer allowlist, and `SameSite=Strict` cookies. | Layered defence. The Origin check also covers login, which has no session yet. |
| D-05 | Requests without Origin/Referer | Allowed through the Origin check (the CSRF token still applies once logged in). | Browsers always send `Origin` on cross-origin unsafe requests. Non-browser clients (curl, tests) send neither. |
| D-06 | Login throttling | In-process counter keyed by client IP + username: 5 failures lock that key for 5 min. Resets on restart and is not shared across workers. | Single-user, single-process, loopback app. No Redis (the brief says to avoid speculative infrastructure). Revisit if multiple workers or LAN exposure become common. |
| D-07 | Password hashing | argon2id with argon2-cffi defaults (RFC 9106 low-memory profile), rehashed on login when parameters change. Length 12–256. | "Strong password hashing". |
| D-08 | Account creation | **Original:** CLI only (`python -m app.cli create-user`), which refuses to create a second user. **Update (2026-09-26):** a browser first-run setup was added as well (D-49). The CLI stays for headless setup and recovery. `set-password` revokes all sessions. | "Single-user", "No public signup". |
| D-09 | Usernames | Case-insensitive, stored lower-case, `[A-Za-z0-9_.-]{3,64}`. | Avoids look-alike duplicates. Strict validation. |
| D-10 | Session lifetime | 7 days absolute, 24 h idle. `last_seen_at` is written at most every 5 min. Both are configurable. | A balance for a personal tool, avoiding a DB write on every request. |
| D-11 | Network exposure | Default bind `127.0.0.1`. A non-loopback `HEXOPS_HOST` makes startup fail unless `HEXOPS_ALLOW_LAN=true`. LAN use should also set `HEXOPS_COOKIE_SECURE=true` behind HTTPS. The Vite dev server always binds loopback. | "Make exposure to LAN an explicit configuration choice." |
| D-12 | OpenAPI docs | Disabled by default (`HEXOPS_ENABLE_DOCS=true` to enable). | Otherwise they would be an unauthenticated route that describes the private API. |
| D-13 | DB access style | Synchronous SQLAlchemy 2 with psycopg 3. FastAPI runs sync endpoints in its threadpool. | Simpler and more readable than async for a single-user app. Long PDF work will run in a background worker (Stage 7, renumbered from 6 per D-02), not in request handlers. |
| D-14 | Theme & language persistence | Stored per browser in `localStorage` (`hexops.theme`, `hexops.lang`). An inline script applies the theme before first paint. Not stored server-side in v1. | No schema needed yet. Easy to move into a `user_preferences` table later. |
| D-15 | Uzbek script | Uzbek Latin, with the official `ʻ` (U+02BB) in `oʻ`/`gʻ`. | Official orthography. |
| D-16 | Language detection | `localStorage`, then the browser language, then English. | Sensible default for three supported languages. |
| D-17 | Placeholder modules | Dashboard, Reports, Projects and Notes pages exist in Stage 1 only as clearly labelled "coming in a later stage" screens. They store and show no data. | The layout can be verified without faking features. |
| D-18 | Toolchain versions | Node 20.19 (Debian 13 package). Vite 8, React 19, React Router 8 (single `react-router` package), Tailwind 4, TypeScript 6. `jsdom` is pinned to v26 because v30 needs Node ≥ 22. | Use what the OS provides. Upgrading Node would allow a newer jsdom. |
| D-19 | shadcn/ui | Components were added with the shadcn CLI (new-york, neutral). The CLI resolved the `@/lib/utils` alias to an unrelated npm package named `cn` and installed it. That package was removed and the imports were fixed. | Supply-chain hygiene. Check `package.json` after future `shadcn add` runs. |
| D-20 | Database runtime | Native PostgreSQL 17 on loopback, no Docker. Separate `hexops` and `hexops_test` databases. The test suite refuses to run if they are the same. | Local-first, fewer moving parts. Tests wipe their own database. |
| D-21 | Visual design | System font stack (SF on Apple devices), neutral greys, one system-blue accent, 12 px radius, no animation except the loading spinner, `prefers-reduced-motion` respected. | "Apple-inspired, restrained". |
| D-22 | Timestamps | `timestamptz` everywhere, in UTC in the application. The UI formats them in the viewer's locale and time zone. | Avoids time zone bugs. |
| D-23 | Stage order vs. requirements roadmap | The requirements list a 7-step roadmap (Projects/Reports/Notes CRUD together, then editor/tags/search/uploads, and so on). The work was split per module instead (D-02). The roadmap's content is covered either way. | Building one module per stage keeps each stage testable. |
| D-24 | Severity vs. CVSS | `severity` is always set by the researcher: `critical/high/medium/low/info`. `cvss_score` (0.0–10.0) and `cvss_vector` are optional and only informational. Nothing derives severity from CVSS automatically. Final in Stage 4. | The requirement says "CVSS or a custom scale". Programs often rate differently from CVSS. |
| D-25 | Report status corrections | Provisional: only the legal forward transitions are allowed (`draft→submitted→triaged→accepted/duplicate/rejected`, `accepted→paid` only for BBP). A mistaken transition can be undone one step. The activity log records it as `correction`, and the step's date is cleared. Final in Stage 4. | The requirement leaves `Paid` and corrections to be decided during implementation. Mistakes happen, and the audit trail must stay honest. |
| D-26 | Bounty payouts | Amount, ISO-4217 currency and `paid_at` are stored on the report. There is no `report_payouts` table in v1. The Dashboard bounty chart groups paid reports by `paid_at` and currency, and never converts between currencies. | The requirement makes `report_payouts` conditional ("if needed"). One payout per report covers the stated use. |
| D-27 | Report ↔ project link | `reports.project_id` is required. The target is taken from the project's scope. There is no free-text target field in v1. | The requirements say "linked project/target"; a required project link covers both. |
| D-28 | Project scope | Scope is a child table (`project_scope_items`). Each row has a `kind` (domain, wildcard, URL, IP, CIDR, other), a `value` stored exactly as entered, an optional `note` and a `position`. Invalid values are rejected with an error and never silently rewritten. There is no out-of-scope list in v1. | Stage 3: "structured list … without silently changing scope entries". |
| D-29 | Tags | Tags apply to Notes only (`tags`, `note_tags`). Report tags from the first plan are dropped. | The requirements data model lists only `note_tags`. |
| D-30 | Evidence storage | Attachments belong to reports only. Files are stored under `data/uploads/` (git-ignored) and the metadata is in the database. | The requirement puts screenshots and PoCs under Reports and names `data/uploads/`. |
| D-31 | Mobile navigation | Phones use a left drawer (Sheet), not a bottom bar. | The requirement allows "drawer or bottom navigation". The drawer is already built and keyboard accessible. |
| D-32 | First-run admin setup | **Original (2026-09-25):** The Stage 2 "first-run local admin setup" is met by the CLI (`create-user`, which refuses a second user). There is no web setup wizard.<br>**Superseded (2026-09-26) by D-49:** the owner asked for a browser setup. The objection above is resolved by allowing it only from loopback clients and only while `users` is empty. | A web wizard would be an unauthenticated account-creation route, which conflicts with "no public registration". |
| D-33 | Uzbek apostrophe | The requirements file uses `‘` (U+2018) in `o‘`/`g‘`. The UI keeps `ʻ` (U+02BB) per D-15. Search (Stage 6) will treat both, and `'`, as the same character. | Consistent orthography in the UI, and tolerance for whatever users type. |
| D-34 | API error shape | Every error is `{detail, code, errors?}` (`app/errors.py`). `code` is a stable identifier that the UI translates; `detail` is English text for developers. Validation `errors[]` carry `field`, the pydantic error type as `code`, and primitive `params` (e.g. `min_length`). They never carry the rejected input. DB connection failures anywhere return `503 database_unavailable`. | One place for the UI to translate from. Inputs can contain passwords. |
| D-35 | Connection detection | The UI probes `GET /api/health` on load and whenever the tab regains focus. It re-probes every 15 s only while the backend is down, and never polls while healthy. A network failure, or a 5xx without the HexOps envelope (the Vite proxy's empty 500, a reverse proxy's 502/504), counts as *unreachable*. Only a 401 leads to the login screen. When the backend comes back, failed queries are refetched. TanStack Query uses `networkMode: 'always'`. | Keeps an outage from looking like a sign-in problem. "No rapid polling". The browser's offline flag doesn't tell us whether a loopback server is up. |
| D-36 | Query retries | Only unexpected HexOps server errors (`internal_error`) are retried, at most twice. Client errors, outages and DB outages are not retried; the health probe handles recovery. | An outage is shown at once instead of after a backoff delay. |
| D-37 | Validation messages | Forms use `noValidate` and do their own checks, which produce the same codes as the backend. Server field errors are shown next to the field. Messages come from the `validation.*` keys and can be overridden per field (e.g. the username format). Disabled submit buttons are no longer used for validation. | Browser-native messages ignore the chosen UI language. A disabled button gives no reason. |
| D-38 | Toasts | A small in-house provider (two always-mounted live regions: polite for info/success, assertive for errors). At most three toasts are shown. They auto-dismiss after 5 s (8 s for errors) and pause on hover or focus. No toast library was added. | Lightweight and accessible. `sonner` would add a dependency for about 80 lines of code. |
| D-39 | Browser tests | Playwright on Chromium and Firefox, run against a dedicated `hexops_e2e` database wiped on each run, using ports 8001 and 5174. The throwaway E2E user is created by `backend/tests/e2e_server.py`. | Real-browser checks without risk to dev data or running dev servers. |
| D-40 | shadcn lint exception | `buttonVariants` is allowed by name in `react/only-export-components` rather than moved out of `button.tsx`. | Keeps the shadcn file as generated, so future `shadcn add` components that import it still work. |
| D-41 | Sharing the dev UI on a LAN | `HEXOPS_UI_HOST` sets the Vite bind address (default `127.0.0.1`). A non-loopback value is refused unless `HEXOPS_ALLOW_LAN=true`. The API stays on loopback and is reached only through the Vite proxy. First used 2026-09-25, on the owner's request, to serve `http://10.13.4.138:5173`.<br>**Update (2026-09-26):** LAN sharing over plain HTTP was switched off at the owner's request. Both servers are loopback-only again; LAN use is documented only behind a local HTTPS reverse proxy (README) and D-51. | Same explicit opt-in as D-11, with the smallest exposure: only the UI port is on the network. Plain HTTP, so credentials are not encrypted in transit; HTTPS is a Stage 8 topic. |
| D-42 | Modular monolith | One process, one bundle, one database; no plugin system, auto-discovery, event bus or services. Backend shared code is in `app/core/`, features in `app/modules/<name>/`. Frontend shared code is in `src/shared/`, features in `src/features/<name>/`, and the composition root is `src/app/`. A module's public interface is `public.py` / `index.ts`; nothing else may be imported across modules. Registration is explicit: `ROUTERS` (`app/main.py`), `app/models.py`, `PAGES` (`src/app/modules.ts`). The rules are enforced by `tests/architecture/test_boundaries.py` and `src/app/architecture.test.ts`. | Owner requirement (2026-09-26): HexOps will keep growing, so modules need clear ownership without speculative frameworks. |
| D-43 | Auth as a module | `auth` stays a feature module rather than moving into core, because it owns tables, a router and a CLI. Other modules use only `app.modules.auth.public` (`require_user`). The account CLI moved to `app/modules/auth/cli.py`; `python -m app.cli` still works through a thin entry point. | Keeps core free of domain tables, and keeps the documented command unchanged. |
| D-44 | Page registry | `PAGES` in `src/app/modules.ts` builds both the routes and the sidebar. Each entry is lazy and gets its own route `errorElement`, rendered inside the shell. | One explicit place to add a page. A failing page leaves navigation working. |
| D-45 | Failed page chunks | `lazyPage` never rejects. If a page's code cannot be loaded, it resolves to a component that throws, so the route's error boundary shows *"This page could not be displayed"* with a Reload button. | Found in Chromium: React Router 8 renders **nothing** when a route's `lazy()` rejects, because the route stays marked lazy and the render tree is cut at the root. The whole app went blank. Browsers cache failed module imports, so recovery is a reload. |
| D-46 | Widget isolation | Self-contained sections, Dashboard widgets first, are wrapped in `ErrorBoundary` one by one, and each has its own `useQuery` with its own loading, empty and error states. There is no single aggregate dashboard request. | "A failure in one page or Dashboard widget does not blank the whole application." |
| D-47 | Translations stay central | Locale files stay in `src/shared/i18n/locales/`, with one namespace per feature (`projects.*`). They are not split into per-feature files. | Three files are easy to keep in sync, and the parity test checks them. Splitting can come later if the files grow unwieldy. |
| D-48 | shadcn paths | `components.json` aliases now point at `@/shared/ui`, `@/shared/lib/utils`, `@/shared/components`. Moving the shadcn files changed only their `@/lib/utils` import path. | Future `shadcn add` output lands in `shared/`. |
| D-49 | First-run setup (security) | `GET /api/auth/setup` (public) reports `{required}`. `POST /api/auth/setup` creates the owner and signs them in, but only when all of these hold: (1) Origin/Referer is trusted; (2) the direct peer **and every `X-Forwarded-For` / `Forwarded: for=` hop** is loopback (the Vite proxy sets `xfwd`, which appends the real client address, so prepending `127.0.0.1` does not help); (3) no user exists. (3) is guaranteed by `uq_users_single_owner`, a unique index on a constant (migration 0002), so the database accepts at most one row, and concurrent requests yield one 201 and 409s. The loopback check runs before body validation, so remote clients learn nothing about the form. Password: 12–256 characters, confirmation checked on the server too (`password_mismatch`), Argon2id via `create_user`; never logged, echoed or stored client-side. The CLI `create-user` uses the same `setup_owner` path. The migration refuses, rather than deletes, if a database already has more than one user. | Owner requirement (2026-09-26). The loopback rule keeps a LAN-shared UI from letting anyone on the network claim the empty instance. The DB constraint is the only race-proof check. `GET` reveals whether the instance is empty; this is acceptable because that state lasts only until setup. |
| D-50 | Shared auth UI pieces | `FormField` (label, input, hint/error with `aria-describedby`) is in `shared/components`. `AuthLayout` and the client-side validators (`features/auth/validation.ts`, mirroring the backend limits and pydantic codes) belong to the auth feature. | Sign-in and setup share one accessible field pattern. Validation codes stay identical on client and server. |
| D-51 | DNS rebinding & proxy trust | **Finding (2026-09-26 review):** the API accepted any `Host`, and `check_origin` trusts "own origin" derived from `Host`. A web page opened on this machine could rebind its domain to `127.0.0.1` and reach `127.0.0.1:8000` directly with matching `Host`/`Origin` from a loopback peer. On an empty database that would pass first-run setup. The Vite server was not affected: it rejects unknown hosts. **Fixes:** (a) the API answers only to `HEXOPS_ALLOWED_HOSTS` (default `127.0.0.1, localhost, ::1`; a non-loopback `HEXOPS_HOST` is added) and returns `400 invalid_host` otherwise, before any route; (b) setup also requires a present, loopback `Origin`, so a LAN browser is refused even behind a proxy that drops `X-Forwarded-For` (nginx defaults). **Remaining assumption:** a non-browser client on the LAN can forge `Origin`, so for those the guarantee rests on the peer and `X-Forwarded-For` checks. Any proxy on this machine must append `X-Forwarded-For` (Vite `xfwd`, Caddy default, nginx `$proxy_add_x_forwarded_for`). uvicorn runs with `proxy_headers=False`, so `request.client` is always the real TCP peer. | Evidence: `app/main.py` (`request_hostname`, `check_host_and_add_headers`), `app/modules/auth/deps.py` (`require_loopback_client`), `app/__main__.py`, `frontend/vite.config.ts` (`xfwd`, `allowedHosts`); tests `tests/core/test_host_header.py`, `tests/auth/test_setup.py`. |
| D-52 | Password change in the UI | `POST /api/auth/password` requires a session, a CSRF token and a trusted Origin. Body: `current_password`, `new_password` (12–256), `new_password_confirm`. The confirmation is checked by pydantic (`password_mismatch`). The router verifies the current password against the stored Argon2id hash (`invalid_current_password`) and refuses a new password that verifies against the current hash (`password_reused`); both are field errors via `core.errors.field_error`. Wrong current passwords share the login throttle (key `password-change:<user id>`, 5 → 429). Success calls the existing `set_password`, which hashes the new password and deletes **all** of the user's sessions, clears the cookies and returns `204` with no body. The frontend clears auth state, and RequireAuth shows the login page with a memory-only notice (`noticeKey`). After sign-in the user returns to the page they were on. The form has a single "Show passwords" checkbox (a native control with a 44 px row), `autocomplete` hints and a hidden username for password managers. | Owner requirement (2026-09-26). Revoking the current session too means a stolen session cannot outlive a password change. Reuse checks compare against the hash, so the password is never stored or compared in plain text. |
| D-53 | Activity log ownership | A separate `activity` module owns `activity_logs`. Other modules write through `activity.public.record()`, which only adds the row to the caller's session, so the event commits atomically with the change or not at all. `project_id` is an indexed plain integer, **not** a foreign key: the history outlives deleted records, and `activity` depends on no other module's tables. `details` holds only field names, status from/to and the record name, never descriptions or scope values. Events: `project.created`, `project.updated {fields}`, `project.status_changed {from,to}`, `project.deleted {name}`. A save that changes nothing records nothing. | Stage 3 "record create/update/status changes"; reusable by Reports, Notes and the Dashboard's recent activity (Stage 6). |
| D-54 | Enum storage | `type`, `status` and `kind` are `VARCHAR(32)` with one named CHECK constraint each (`ck_<table>_<name>`), not native PostgreSQL enums. Autogenerate emitted duplicate CHECKs; migration 0003 was hand-edited, and `alembic check` confirms model and schema match. | Adding a value later is an ordinary migration; native enums need `ALTER TYPE`, which is awkward in transactions. |
| D-55 | Project update semantics | `PUT` replaces the whole project, including the ordered scope (the form always sends everything). The scope is rewritten only if it changed; `updated_at` is bumped explicitly, also for scope-only changes. Delete is allowed; it cascades to scope items and keeps the activity history (D-53). No optimistic locking: single user, last write wins. Stage 4 decides what deleting a project with reports means (likely refuse). | Simple, predictable form semantics. |
| D-56 | Scope validation | Values are validated per kind and **never rewritten**. Surrounding whitespace, control characters, a CIDR with host bits set (`10.0.0.5/24`) and malformed values are rejected with field errors (`scope.<i>.value`), not "fixed". Domain: at least two labels, IDN allowed (checked via IDNA). Wildcard: `*.` plus a domain. URL: http(s) with a host (domain, IP or `*.`). IP: v4/v6. CIDR: strict network. Other: any text. Duplicates (same kind and value; case-insensitive for domain and wildcard) are rejected on each repeat. Limits: 500 items, 512-character values, 1000-character notes. The project **name** is trimmed; that is the only normalization. | "Validate and normalize inputs without silently changing scope entries." |
| D-57 | Project list queries | `GET /api/projects`: `q` (case-insensitive substring match on the name, with `%`, `_` and `\` escaped so they match literally), `type`, `status`, `sort` ∈ {updated_at, created_at, name (lower), start_date, status}, `order`, `page`, `size` ≤ 100. NULL start dates sort last in both directions, and `id` breaks ties so pages are stable. Items carry no description or scope, only `scope_count`. Indexes: `(status, updated_at)`, `updated_at`, `start_date`, `type`, `lower(name)`. The UI keeps filters in the URL (shareable; Back and reload restore them), sends search 300 ms after typing stops, and keeps the previous page visible while the next one loads. | Server-side pagination, filtering and sorting; no rapid requests. |
| D-58 | Native form controls | Selects use the native `<select>` (`shared/ui/native-select`), dates use `<input type="date">`, the show-password toggle is a native checkbox, and delete confirmation is a Radix AlertDialog (focus trap, Escape, focus returns to the trigger). | Native controls give the best keyboard, screen-reader and phone behaviour with the least code. |
| D-59 | Validation message registry | Module-specific error codes are translated under `validation.codes.<code>` (with the error params interpolated). `fieldErrorMessage` falls back to that key before the generic "invalid". | New modules add translations, not code, for their error codes. |
| D-60 | Deleting a project with reports | Refused. `reports.project_id` is `ON DELETE RESTRICT`. The projects service catches the FK violation, rolls back (including its `project.deleted` event) and returns `409 project_has_reports`. The UI shows a translated message. Projects does not import Reports: the database enforces the rule. Deleting a **report** is allowed and removes its evidence files (the confirmation says how many). | Stage 4: "must not be silently deleted along with its reports or evidence". A DB constraint cannot be bypassed by a future code path. |
| D-61 | Severity vs CVSS | `severity` (critical/high/medium/low/info) is always the researcher's own choice and required. `cvss_score` (0.0–10.0, one decimal) and `cvss_vector` (CVSS 3.0/3.1/4.0 syntax) are optional and independent; neither is derived from the other, and no score is computed from a vector. The UI shows the CVSS qualitative rating for the score as a hint and says when it differs from the chosen severity, but never changes either value. Decimals travel as strings. | "Do not silently overwrite either." Programs often rate differently from CVSS. |
| D-62 | Evidence storage | Evidence is part of the reports module (`reports/storage.py`, table `report_attachments`), so no cross-module cycle is needed.<br>**Files:** stored flat in `uploads_dir` (0700) as random `token_hex(16)` names (0600). `path_for()` accepts only `^[0-9a-f]{32}$` and checks the resolved parent. Display names are sanitized: no directories or control characters, NFC, at most 255 characters.<br>**Type:** an extension allowlist plus a content check (image and PDF signatures; text must be valid UTF-8 with no NUL). The client's content type is ignored. SVG, archives and executables are refused. Text, including HTML, is served as `text/plain; charset=utf-8`.<br>**Limits:** `Content-Length` is required (411 without it) and checked before multipart parsing (413), and the byte count is enforced again while streaming. Up to 100 files per report.<br>**Downloads:** `attachment` with an RFC 6266 filename, `nosniff`, `CSP: default-src 'none'; sandbox`, `no-store`.<br>**Consistency:** upload streams to a `.tmp-*` file, validates it, atomically renames it, then commits the row; if the commit fails the file is deleted. Deletes commit the row first and then unlink the file (a failure leaves only a harmless orphan, which is logged). Leftover temp files are swept at startup. | Stage 4 file-safety requirements; no path, type or name comes from the client. |
| D-63 | Status workflow API | Status changes only through `POST /api/reports/{id}/status {to, correction?, at?}`; create/update never touch status (it is `extra_forbidden`). Forward moves follow the workflow; `accepted → paid` only for BBP (`paid_requires_bbp`, also a DB CHECK). A correction must be explicit (`correction: true`), may undo exactly one step and clears that step's date (`invalid_status_correction` otherwise). Reaching a final status and then changing it is done by an undo followed by a new move. `at` backdates a step: it must have a time zone, cannot be in the future (5-minute tolerance) and cannot be earlier than a previous step's date. Refused moves return 409 with a code the UI translates and leave no history. The API returns `next_statuses` and `correction_to`, so the UI offers only legal moves. | Stage 4 workflow and "record every transition and correction". Supersedes the provisional D-25 with the same rules. |
| D-64 | Actor in history | `activity_logs.actor_user_id` (plain integer, no foreign key, like `project_id`) is written for every event since migration 0004. The API returns the username (via `auth.public.usernames`). Events from before Stage 4 show no actor. Report events carry `project_id`, so a project's history includes its reports' events, linked to the report. | "With the actor and timestamp." |
| D-65 | Bounty fields | Amount (0 to 12 digits plus 2 decimals) and ISO-4217-shaped currency (three uppercase letters), both or neither (DB CHECK as well), and only on BBP reports (`bounty_requires_bbp`; the form hides them for other types and sends null). Paid does not require an amount. | Requirement: bounty optional; Paid is a BBP concept. |
| D-66 | Report body editor (Stage 4) | A monospace `<textarea>` with a character counter (200,000 max). The body is saved as Markdown and shown as preformatted source on the detail page. Stage 5 replaces both with the shared Markdown editor and safe preview; no second editor is built now. | "Functional, accessible text editor now without duplicating a complex editor." |
| D-67 | Feature dependencies (frontend) | `projects` → `reports` (the Reports section on a project page) and `projects`, `reports` → `activity`. `reports` does **not** import `projects`: its project picker calls the Projects HTTP API (`/api/projects`), its public contract, so there is no import cycle. Shared building blocks added: `Section`, `ConfirmButton`, `native-select`, `alert-dialog`, `Pagination`. Layout rules learned: container queries (`@container`/`@sm:`) for content in narrow side columns, and buttons with long translated labels need `whitespace-normal shrink max-w-full`. | Module boundaries (D-42) without cycles. |
| D-68 | Notes ↔ projects | `notes.project_id` is optional and `ON DELETE SET NULL`: deleting a project keeps its notes, unlinked (the project delete dialog says so). Unlike reports (D-60), a note is valid without a project, so blocking the delete would add friction without protecting anything. Note events carry `project_id`, so a project's history lists them, linked to the note. | Requirement: notes link to a project optionally. |
| D-69 | Tags | Tags live in `tags`, shared by notes through `note_tags`, and are normalized: trimmed, NFC and lower-case.
